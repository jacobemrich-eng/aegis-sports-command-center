# AEGIS Launch Capacity Plan — v9.1.2

## Scaling principle
End-user count must not determine provider-call count. User/browser reads consume the shared persistent board. Upstream provider calls are generated by the centralized Autopilot refresh cadence.

## Current request path
1. Browser/user -> Shared Data Gateway
2. Shared persistent board -> response
3. Autopilot -> memory cache -> durable provider cache -> provider router
4. Provider router -> primary provider
5. On eligible transient primary failure -> SportsGameOdds secondary
6. If upstreams fail -> bounded stale durable cache, explicitly labeled stale

## Launch safety
- Keep the current 18/day and 450/month development governor until a production data plan is selected.
- Do not remove freshness gates merely because a secondary provider exists.
- Do not promise unlimited refreshes. Commercial provider capacity is finite even when user traffic is shared.
- User growth should increase web/compute traffic, not linearly increase upstream odds calls.
- Scale Render/Supabase independently from odds-provider contracts.

## Secondary-provider scope
SportsGameOdds failover initially covers MLB and NCAAF full-game h2h/spreads/totals. Deep event markets remain protected by the durable cache and primary provider until a cross-provider event-ID map is proven.

## Capacity formula
Approximate upstream demand from schedule design, not user count:

daily_provider_requests ~= scheduled_refreshes + targeted_refreshes + deep_market_refreshes + grading/result requests

User page views should normally add zero upstream odds requests while a usable shared board exists.

## Launch stages
1. Development: current quota governor; secondary key optional.
2. Private beta: configure secondary key, perform controlled failover test, measure provider objects/requests and Supabase row-cache size.
3. Paid/public beta: choose provider tier from measured refresh demand; raise AEGIS budgets deliberately.
4. Public launch: paid always-on hosting, production data contract(s), alerts for provider saturation, and usage dashboards.
